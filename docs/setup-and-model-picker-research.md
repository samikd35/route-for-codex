# Adding Route models to Codex

**Product proposal.** Give first-time users one action, **Connect to Codex**. Register Route as an additional provider, publish its own model catalog, and label entries **Route 6.2 Sol** and **Route 6.2 Astra**. Make **Use Route for new chats** a separate preference. The desired new-chat picker shows both accounts and preselects the preferred row. Provider registration and branded labels can ship independently of that combined picker. The feasibility of the stock picker is discussed below.

Research date: November 23, 2026. The local installations report Codex CLI `0.171.0-alpha.13`, ChatGPT Desktop `26.1117.41037` (build `29803`), and Ollama `0.40.16`. The public Codex source links below use the tag matching that CLI. The same provider-selection behavior is documented in the stable `0.171.0` source. [Codex stable app-server documentation](https://github.com/openai/codex/blob/rust-v0.171.0/codex-rs/app-server/README.md#model-catalog-provider-requirements)

## How Ollama adds models

Ollama delivers two different experiences. Its desktop app offers an **Apps → ChatGPT (Desktop)** toggle. After setup and any requested restart, the selected Ollama models appear alongside native models in Codex mode. Turning off the integration restores the previous configuration. Its terminal command, `ollama launch codex`, refreshes an Ollama catalog and launches Codex with a dedicated profile. In that CLI session, `/model` lists the tool-capable Ollama models. [Ollama Desktop instructions](https://docs.ollama.com/integrations/chatgpt) · [Ollama CLI instructions](https://docs.ollama.com/integrations/codex)

The Desktop launcher saves the prior configuration, obtains the native catalog, writes a combined picker catalog and creates a separate list of models to dispatch to Ollama. It sets root `openai_base_url` to a loopback router, removes explicit `model_provider`, and sets root `model_catalog_json` to the combined file. Every affected Codex inference request reaches that listener. Regular Chat is outside this integration. Ollama's current stable release retains this design. [Installed-tag setup](https://github.com/ollama/ollama/blob/v0.40.16/cmd/launch/codex_app.go#L101-L143) · [Installed-tag config writes](https://github.com/ollama/ollama/blob/v0.40.16/cmd/launch/codex_app.go#L312-L353) · [Stable config writes](https://github.com/ollama/ollama/blob/v0.40.17/cmd/launch/codex_app.go#L325-L333)

The router looks up the request's model in the Ollama-only list. For matches it selects the Ollama upstream and constructs outgoing headers from an allowlist that excludes Codex credentials. For native traffic it selects ChatGPT or the OpenAI API according to the incoming auth context and retains the corresponding credentials. It handles body normalization and compaction, and declines WebSocket upgrades to use HTTP per request. A copy of the model names alone would leave all requests on the same inference path. [Model dispatch and transport](https://github.com/ollama/ollama/blob/v0.40.16/internal/proxy/codex_desktop.go#L157-L265) · [Header handling](https://github.com/ollama/ollama/blob/v0.40.16/internal/proxy/codex_desktop.go#L359-L375) · [Documented Desktop behavior](https://docs.ollama.com/integrations/chatgpt#codex-behavior-and-limits)

The combined file is a snapshot. Ollama tries the matching client’s model catalog, then cache and bundled fallbacks. Its merge deduplicates slugs, deliberately adjusts native entries’ API-key visibility, and gives Ollama models their own ordering. Route would need an explicit policy for native account access, freshness and ordering if it adopted the same architecture. Two independent installers also cannot own the same effective base URL or root catalog simultaneously without arranging how to compose and restore them. [Ollama’s catalog acquisition](https://github.com/ollama/ollama/blob/v0.40.16/cmd/launch/codex_app.go#L1516-L1572) · [Catalog merge](https://github.com/ollama/ollama/blob/v0.40.16/cmd/launch/codex_app.go#L1000-L1039)

## What Codex exposes

| Task | Behavior in the documented client or tagged protocol |
| --- | --- |
| Register Route | A named table under `[model_providers.route]` registers a custom connection. The app server’s `modelProvider/list` enumerates OpenAI and explicitly configured providers. Saving a provider can leave the existing default in place. [Provider discovery and configuration](https://github.com/openai/codex/blob/rust-v0.171.0-alpha.13/codex-rs/app-server/README.md#model-provider-configuration) |
| Supply just Route’s model metadata | `model_providers.route.model_catalog_url` gives that provider its own endpoint. Codex expects a version-compatible `ModelsResponse`, sends provider credentials and appends `client_version`. Command-backed auth also supports discovery at the default `/models` under the provider base URL. An effective top-level `model_catalog_json` overrides discovery and replaces the bundled catalog. The gateway guide documents HTTPS deployment. [Serve a remote catalog](https://learn.chatgpt.com/docs/enterprise/roll-out-a-gateway#serve-a-remote-catalog) · [Endpoint contract](https://learn.chatgpt.com/docs/enterprise/roll-out-a-gateway#implement-the-catalog-endpoint) |
| Select Route in stock clients | Desktop documents **Settings → Model Providers → Switch provider**, followed by a new chat. CLI documents **/config → Sessions → Model providers**, **Space** to select the default, then **/new**. Availability of the switch can depend on policy. A CLI launch profile can also select Route for a single invocation. [OpenAI gateway setup](https://learn.chatgpt.com/docs/enterprise/connect-to-a-gateway#configure-the-provider) · [CLI profiles](https://learn.chatgpt.com/docs/config-file/config-advanced#profiles) |
| List a provider’s models | `model/list` without a selector returns the current default provider’s models. Supplying `modelProvider` lists that one provider. A client can ask for two lists and assemble its own provider-qualified new-chat menu. The documented stock workflow selects a provider first. [Catalog selection](https://github.com/openai/codex/blob/rust-v0.171.0-alpha.13/codex-rs/app-server/README.md#L147-L162) · [List parameters](https://github.com/openai/codex/blob/rust-v0.171.0-alpha.13/codex-rs/app-server-protocol/schema/typescript/v2/ModelListParams.ts#L5-L21) |
| Choose a provider per chat | `thread/start` accepts both `modelProvider` and `model`. Existing chats retain their provider across default changes and resume. `turn/start` accepts a new model on that provider. Separate registered providers therefore support separately attributed new chats, while in-place switching between providers would need additional client support or a router behind one provider. [New-chat parameters](https://github.com/openai/codex/blob/rust-v0.171.0-alpha.13/codex-rs/app-server-protocol/schema/typescript/v2/ThreadStartParams.ts#L12-L16) · [Provider retention](https://github.com/openai/codex/blob/rust-v0.171.0-alpha.13/codex-rs/app-server/README.md#L385-L397) · [Turn parameters](https://github.com/openai/codex/blob/rust-v0.171.0-alpha.13/codex-rs/app-server-protocol/schema/typescript/v2/TurnStartParams.ts#L47-L56) |

## Naming and billing

For a Route-only provider catalog, give the existing `gpt-6.2-sol` entry the display name **Route 6.2 Sol**. The provider identifies the connection, the slug identifies the upstream model and the display name supplies the label. The same applies to **Route 6.2 Astra** and other models for which the user’s key has access. A description such as “Uses your OpenAI API key” makes the account distinction visible. Preserve the entry's instructions, reasoning efforts, tools and context metadata. The tagged CLI tests exercise custom display names in both pickers while retaining the selected slug. [Codex catalog fields](https://learn.chatgpt.com/docs/enterprise/roll-out-a-gateway#model-catalog-reference) · [Codex display-name tests](https://github.com/openai/codex/blob/rust-v0.171.0-alpha.13/codex-rs/tui/src/chatwidget/tests/model_display_name_tests.rs#L7-L58)

For a *single combined catalog*, the native and Route entries need distinct slugs. An example mapping is `gpt-6.2-sol` for the existing native route and `route-6.2-sol` for the entry displayed as **Route 6.2 Sol**. A dispatcher must accept the latter and translate it to `gpt-6.2-sol` on the API-key request. It must preserve the native route’s own credentials, reject unrecognized Route aliases without billing another account, and keep alias-specific metadata consistent across reasoning, tools, compaction and resumed turns. This would change Route’s current body-preserving relay and local-token credential boundary. [Codex alias requirements](https://learn.chatgpt.com/docs/enterprise/roll-out-a-gateway#choose-model-names-and-routes) · [Codex catalog uniqueness](https://learn.chatgpt.com/docs/enterprise/roll-out-a-gateway#implement-the-catalog-endpoint) · [Route architecture](../ARCHITECTURE.md)

## Two experiments on the installed Codex build

I ran the installed app server in a disposable Codex home. Two loopback providers served deterministic catalogs and Responses events. Each used a dummy credential helper. Both advertised the real slug `gpt-6.2-sol`. The ordinary provider was the fixture default. These experiments exercised catalog discovery, chat creation and the outgoing HTTP request. They used no paid inference and made no changes to the user's Codex settings.

| Experiment | Observation |
| --- | --- |
| One catalog per provider | `modelProvider/list` returned OpenAI and both fixture providers. The ordinary provider and the unscoped list returned **Native fixture Sol**. The Route-scoped list returned **Route 6.2 Sol**. Both catalog endpoints received the expected dummy bearer token over loopback HTTP. Starting one chat per provider gave two completed turns. Each endpoint received its own POST with the identical upstream slug `gpt-6.2-sol`. |
| One global catalog with two labeled rows | Both provider-scoped lists returned the same two rows, and Codex skipped the provider catalog endpoints. Selecting each row under the ordinary provider sent **both** requests to that provider. The second request contained the Route alias verbatim. This reproduces the billing ambiguity of simply concatenating catalogs. |

The ordinary endpoint simulated the native provider for this experiment. The results establish the protocol behavior and display metadata. An acceptance test of the graphical picker needs the actual signed-in app and a normal new chat. Existing live tests on this Mac separately established that CLI coding works through Route and that stock Desktop and CLI Route sessions did not expose built-in image generation. A picker or branding change needs its own image regression check. [App-server model listing](https://learn.chatgpt.com/docs/app-server#list-models-model-list) · [Route qualification procedure](qualification.md#repeat-the-release-checks)

## First-run design

1. **Install and open Route.** On macOS, distribute a signed, notarized installer that includes Route.app, Caddy and the CLI. Route detects the installed Codex client and its catalog version. Add the actual bundled CLI location to discovery so a Desktop user can use a compatible app installation without separately configuring a shell. The current discovery code checks PATH and a few older fixed locations. [Route packaging](../tools/package.py) · [Current discovery](../route/models.py) · [Apple distribution guidance](https://developer.apple.com/developer-id/)
2. **Paste an API key and press Connect to Codex.** Show the two-request API usage before the click. Use the existing OS credential store, discovery and streamed tool challenge. Keep an eligible prior selection, otherwise use Sol at medium when available, and show the model chooser when an explicit selection is needed. Show the session-only choice if secure storage is unavailable. A rejected key, no eligible models, and a failed challenge each get a specific recovery action. [Existing setup policy](../ARCHITECTURE.md#one-setup-for-both-clients)
3. **Show the tested result and a next action.** Example after success: **Ready · Route 6.2 Sol**, with **Open Codex** and a separate **Use Route for new chats** preference. Show where to select Route on that client if its stock picker requires a provider switch. Offer a restart when that build needs to reload configuration, without interrupting an active turn. Record readiness for the tested key generation and model. Today, Status can say Connected as soon as Caddy is listening, even after discovery or the challenge failed. [Status and setup code](../route/cli.py) · [Codex gateway setup](https://learn.chatgpt.com/docs/enterprise/connect-to-a-gateway#configure-the-provider)
4. **Give terminal users one unambiguous command.** Proposed public entry point: `route-for-codex`. On first use it starts guided setup. It can retain explicit `connect`, `status`, `disconnect` and `forget` for scripting. Debian already installs this name. The macOS installer tested during this research supplied `/usr/local/bin/route`, and bare `route` resolved to `/sbin/route` on this Mac. Keep the credential helper bound to a real executable path through upgrades. [Current native package layout](../tools/package.py) · [Credential helper registration](../route/cli.py)

## How I would ship it

**First release — setup, provider registration and labels.** Add an authenticated, provider-scoped catalog endpoint alongside the existing Responses endpoint. The fixture verified the credential-helper flow on loopback HTTP in this build. Serve only the key's eligible entries with metadata compatible with the requesting client version. Derive the Route display label from the known family and version, preserve meaningful suffixes for future variants, and change only presentation fields. Keep the current provider and its model by default on first connect. If the user opts into Route, select it for new chats. The stock provider switch and an optional dedicated CLI profile are usable fallbacks. Users can retain both providers at this stage. The stock picker can still show just the active provider's rows. [Current catalog filtering](../route/models.py) · [Current activation](../route/cli.py) · [Codex catalog contract](https://learn.chatgpt.com/docs/enterprise/roll-out-a-gateway#implement-the-catalog-endpoint)

**Exact same-menu experience — choose the implementation deliberately.** My preferred design is a new-chat picker grouped by **ChatGPT** and **Route · your OpenAI API key**. Fetch both provider catalogs and keep each choice keyed by the pair of provider ID and model ID. Selecting a row starts the chat with that pair. Making Route the default only preselects its row. A native stock implementation needs the host picker to offer this interaction. A Route-owned launcher could offer it earlier, subject to proving the handoff opens the intended chat in Desktop. If the product must deliver both groups *inside unmodified Desktop now*, the Ollama-style combined catalog and router is the credible prototype. It makes the availability of ordinary Codex inference depend on a local component and expands the credential boundary to native traffic. Support for compaction, cancellation, account changes and coexistence with Ollama would be release work. Treat that as a product decision before committing to it. [Tagged chat-start contract](https://github.com/openai/codex/blob/rust-v0.171.0-alpha.13/codex-rs/app-server-protocol/schema/typescript/v2/ThreadStartParams.ts) · [Ollama Desktop design](https://docs.ollama.com/integrations/chatgpt)

**Migration.** For an existing user, use Route's per-setting journal to retire the top-level Route catalog only if the current value still matches what Route wrote. Preserve the user's choice of default, restore prior catalog settings when applicable, and respect subsequent manual edits. If the restored catalog or a managed policy forces a global catalog, surface the conflict and offer the scoped CLI profile where permitted. Preserve unrelated providers, including Ollama. Verify Disconnect, Forget and upgrading a currently connected installation. [Settings journal](../route/settings.py) · [Managed catalog precedence](https://learn.chatgpt.com/docs/enterprise/roll-out-a-gateway#serve-a-remote-catalog)

**Acceptance demonstration.** Install on a clean Mac and connect without touching a terminal. As an existing user, start one ordinary Sol chat and one Route Sol chat from the proposed selection flow. Check their actual providers, upstream model IDs, billing paths and supported reasoning levels. Repeat after making Route the default, restarting, rotating to a key without Astra, and disconnecting. An already-open native chat must continue on its original provider. A rejected Route request must surface the error without falling back to another billing path. On a machine with Ollama enabled, verify its entries and restore behavior as well. Record separately whether the two rows appeared in the stock picker, a provider switch, or Route's own launcher.
